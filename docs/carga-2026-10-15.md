# Carga, concurrencia y volumen · 15 de octubre de 2026

Corridas en la Mac de desarrollo (Apple Silicon, Node 24.21, Chrome 155 de la Mac para los PDF), con el build de
producción (`next build` + `next start`, puerto 3200), la IA fija (`NELTUME_LLM=fijo`), Starken simulado y sin
sincronizar feriados. Cada corrida usa una base temporal con el catálogo real (`COTIZADOR_2026.xlsx`, 8.772
productos); `data/` no se toca. Sin gasto de IA.

Cómo repetirlas:

```sh
npm run build
npm run carga -- --personas 4 --rondas 8                       # mixta sobre Servicio, sin HTTP
npm run carga:http -- --sembrar 20000                          # ab sobre las rutas, con 20.000 cotizaciones
npm run carga:http -- --sembrar 20000 --sin-ab --minutos 15 --personas 4   # resistencia por HTTP
npx vitest run tests/carga-concurrencia.test.ts --silent=false # concurrencia y volumen, con números
```

`scripts/carga-http.ts` arranca `next start` con `BETTER_AUTH_URL=https://127.0.0.1:<puerto>` (producción lo exige)
y le habla por HTTP directo, sin el proxy TLS: mide el servidor y no el proxy.

## Hallazgo corregido: memoria de las fechas

`fechaLocal` e `inicioDiaSantiago` (`src/negocio/vigencia.ts`) creaban un `Intl.DateTimeFormat` con zona horaria en
cada llamada, y el historial las llama por fila. Esa memoria (ICU, nativa) solo se libera cuando el recolector de
JavaScript pasa, y con el heap casi vacío pasa poco:

| Medida | Antes | Después |
|---|---:|---:|
| 2.000 listados del historial en un proceso (20.000 cotizaciones), RSS | 1.709 MB | 275 MB |
| `next start` tras la ráfaga de `ab` (filtro por fechas, c=8), RSS de Node | 1.787 MB | 606 MB |
| `next start` tras toda la ráfaga de `ab`, RSS de Node | 1.116–2.150 MB | 821 MB |

Ahora los dos formateadores se crean una vez. Prueba: `tests/carga-concurrencia.test.ts` («Memoria nativa de las
fechas»). Quedan otros `new Intl.NumberFormat` por llamada en `precios.ts` y `medidas.ts` (sin zona horaria, más
livianos); no se tocaron.

## Carga mixta sobre Servicio (`npm run carga`)

4 personas × 8 rondas en 11,4 s: 32 cotizaciones emitidas (N° 323–354), 24 notas, sin errores internos, sin
números quemados, base íntegra. Las 17 ediciones con versión vieja de otra persona respondieron 409.

## Carga HTTP con `ab` (20.000 cotizaciones, después del arreglo)

`ab -n 2000 -c 8` (el chat: `-n 1000 -c 4`, cada uno crea un borrador). Base de 40,8 MB al arrancar (46,8 MB al
terminar). `next start` responde en 1,2 s con 244 MB de RSS. Ninguna respuesta distinta de 2xx.

| Ruta | req/s | p50 ms | p95 ms | p99 ms | máx ms | RSS Node MB |
|---|---:|---:|---:|---:|---:|---:|
| GET /api/salud (sin sesión) | 5.145 | 1 | 3 | 4 | 4 | 445 |
| GET /login | 1.398 | 5 | 8 | 12 | 29 | 661 |
| GET / (con sesión) | 1.211 | 6 | 9 | 10 | 20 | 681 |
| Historial, página 1 (30 filas) | 92 | 86 | 89 | 94 | 104 | 689 |
| Historial, página 200 | 28 | 284 | 288 | 294 | 300 | 504 |
| Búsqueda «cliente 1999» | 106 | 75 | 78 | 82 | 87 | 539 |
| Filtro emitidas + rango de fechas | 100 | 80 | 83 | 91 | 99 | 606 |
| GET /api/catalogo | 47 | 169 | 170 | 171 | 174 | 664 |
| POST chat (borrador nuevo) | 24 | 167 | 250 | 472 | 1.800 | 821 |

Con 300 cotizaciones el historial responde en 2–7 ms: con 20.000 cada página cuesta ~80 ms y la página 200, ~290 ms,
porque el listado ordena por una expresión (`COALESCE(fecha_anulacion, nota, emisión, actualizada)`) que no tiene
índice y SQLite ordena todo en cada consulta. Para una persona es imperceptible; si el volumen real se acerca, un
índice sobre esa fecha (columna calculada) lo resolvería.

Con `--heap-mb 512` (heap de V8 acotado, como en un contenedor) la misma ráfaga y 4 minutos de resistencia
terminaron sin errores ni OOM.

## Resistencia (acortada)

El plan pedía 2 a 8 horas; se corrió **acortada**: 18 minutos con 3 personas (antes del arreglo) y 15 minutos con 4
personas (después), sobre 20.000 cotizaciones. Cada ronda: chat → editar → historial → búsqueda → abrir → emitir con
PDF → aprobar → anticipo → nota con PDF → saldo (un tercio de las rondas: duplicar y eliminar).

| | 18 min, 3 personas (antes) | 15 min, 4 personas (después) |
|---|---:|---:|
| Rondas / solicitudes | 1.685 / 15.730 | 2.296 / 21.434 |
| Respuestas 5xx | 0 | 0 |
| PDF emitidos (cotización + nota) | 1.685 + 1.125 | 2.296 + 1.533 |
| Números quemados / PDF faltantes | 0 / 0 | 0 / 0 |
| integrity_check | ok | ok |
| Emitir p50 / p95 / máx (ms) | 909 / 1.446 / 2.385 | 802 / 1.040 / 1.915 |
| Chat p50 / p95 (ms) | 108 / 265 | 69 / 186 |
| Historial p50 / p95 (ms) | 40 / 79 | 26 / 44 |
| RSS de Node: mín → máx, final (MB) | 470 → 803, 720 | 285 → 714, 695 |
| Base al terminar | 64,9 MB, 22.589 cotizaciones | 71,0 MB, 22.297 cotizaciones |

Sin degradación: la mediana del primer y del último tercio es la misma en todas las acciones, salvo emitir y
generar la nota (+13 % en la corrida de 4 personas, 753 → 854 ms; la carpeta de PDF pasa de 0 a 3.800 archivos). El
RSS de Node se estabiliza en ~690 MB a los 3 minutos y no crece. El árbol con Chromium oscila entre 1,4 y 2,5 GB
según cuántos PDF haya en curso: es el Chrome de la Mac, más pesado que el Chromium de Debian (en Docker el pico
medido fue 1.027 MiB de 1.536, sección 7). Registro del servidor sin errores.

Falta la corrida de varias horas (`--minutos 240`) y, mejor, repetir esta dentro del contenedor con su `mem_limit`.

## Concurrencia y volumen (`tests/carga-concurrencia.test.ts`)

- **Respaldo en caliente:** `npm run respaldar` mientras otra conexión crea cotizaciones sin parar (3.000 en la base):
  64 escrituras en 157 ms, ninguna falla, copia íntegra y consistente.
- **Varios PDF a la vez con uno vencido:** 5 simultáneos, uno con plazo de 1 ms: 4 PDF en 609 ms, el vencido
  responde `pdf_no_disponible` sin dejar temporales y el navegador sigue sirviendo.
- **Pico de memoria de un libro legítimo:** xlsx sintético de 20.000 filas con relleno (1,2 MB comprimido): pico RSS
  265 MB (+190 MB), 407 ms. La planilla real: 183 MB (+107 MB), 230 ms.
- **Dos usuarias en la misma cotización** (nuevo): guardan a la vez con la misma versión → una 200 y otra 409, sin
  pisarse; la que perdió recarga y repite y quedan los dos cambios. Una escribe en el chat mientras la otra guarda →
  el chat responde 409 y no deja el mensaje a medias. Emiten la misma a la vez → un solo número.
- **Volumen, en proceso:** 20.000 sembradas en 4,9 s; listado 9 ms, última página 74 ms, búsqueda 7 ms, filtro 7 ms;
  CSV en 5 partes de 0,5 a 1,6 s cada una, sin filas perdidas ni repetidas. Por HTTP, ver la tabla de `ab`.

## Notas de la herramienta

- La primera versión de `carga-http.ts` dejaba la salida del servidor en una tubería; como `ab` se lanza con
  `spawnSync`, nadie la vaciaba y el servidor se detenía al llenarla (≈900 mensajes del chat), lo que parecía una
  solicitud colgada. Ahora el registro va directo a un archivo. No afecta a la aplicación: en Docker la salida la
  lee el motor de contenedores.
- `next build` en una copia nueva del repositorio (sin `data/cotizador.sqlite`) falló con `SQLITE_BUSY`: los
  procesos que recolectan las páginas crean la base a la vez. El Dockerfile ya corre `npm run auth:migrar` antes del
  build; en una copia nueva basta repetir el build o crear la base antes.
