# Neltume · Asistente cotizador interno

Cotizador interno de Neltume para Paula y Paulette: pedido por chat, cotización revisable, PDF con número correlativo y, tras la aprobación del cliente, pagos, nota de pedido a fábrica, producción, despacho y facturación. El catálogo cubre puertas sólidas, enchapadas en Mara y prepintadas, marcos sólidos y sets Pino Finger (desnudos o enchapados en Mara), molduras y piezas T, además de pedidos especiales fuera del catálogo. Las familias son `PUERTA`, `MARCO`, `PIEZAS_T` y `MOLDURA` (`src/catalogo/tipos.ts`). Se administra desde la propia aplicación (**Ajustes** y **Catálogo**). No envía mensajes ni documentos a clientes: la vendedora descarga o comparte el PDF.

**¿Operas el cotizador sin conocimientos técnicos?** Usa el [manual operativo](docs/manual-operativo.md): entrar, cuentas, clave de IA, Starken, respaldo, restaurar, actualizar y qué hacer si algo falla. Dentro de la aplicación, la guía **«Cómo funciona»** (`/ayuda`) explica el recorrido de una cotización. Este README es la referencia técnica; las reglas de cálculo están en [docs/reglas-negocio.md](docs/reglas-negocio.md) y la guía del servidor en [docker/LEEME.md](docker/LEEME.md).

## Arranque inicial

Requisitos: Node.js 22.13+ (verificado con 24), npm y Google Chrome/Chromium. Coloca la planilla oficial en `datos-privados/COTIZADOR_2026.xlsx`. Las cinco planillas y la transcripción entregadas ya quedaron resguardadas en `datos-privados/`, sin modificar su contenido.

Crea `.env.local` a partir de `.env.example` y genera `BETTER_AUTH_SECRET` para sesiones y cifrado con `openssl rand -base64 32`. La clave de CommandCode es opcional en el archivo: una persona administradora puede guardarla desde **Ajustes**. En producción, configura también `BETTER_AUTH_URL` con el origen HTTPS público. Sin clave de IA, el login y la pantalla siguen disponibles, pero el chat explica cómo configurar el asistente.

```sh
npm install
npm run importar -- datos-privados/COTIZADOR_2026.xlsx
npm run auth:migrar
npm run usuarios -- crear admin@example.com Admin
npm run dev
```

Reemplaza `admin@example.com` por el correo real de la persona responsable. En vez de la terminal, mientras la base no tiene ninguna cuenta la página de inicio de sesión muestra **«Crear la primera cuenta»** y pide un código de un solo uso que el servidor escribe en su registro (`src/servidor/primer-arranque.ts`, `src/app/login/primera-cuenta.tsx`, `src/app/api/primer-arranque/`). Vale el último código del registro; vence en 24 horas y se anula tras 10 intentos fallidos. En desarrollo aparece en la consola de `npm run dev` al abrir la página de inicio de sesión (o con `npm run primer-arranque`); con Docker, con `docker compose logs cotizador | grep -A2 "Código de un solo uso"`. En disco solo queda su hash (`data/primer-arranque.json`), que se borra al crear la cuenta; con al menos una cuenta, la ruta responde 404.

Todas las cuentas tienen rol `admin`: quien administra puede crear otras desde **Ajustes → Usuarios**. Mantén siempre **dos administradoras activas**: si una olvida su contraseña, la otra la restablece desde Usuarios sin terminal. La página avisa cuando queda una sola, y la API no deja desactivar la propia cuenta ni la última administradora activa (`src/app/api/usuarios/route.ts`). Cada cambio de cuentas (crear, editar, desactivar, activar, restablecer la clave), también los hechos por terminal o por el primer arranque, queda en **Ajustes → Usuarios → Registro de cambios**, que muestra los 50 más recientes (`src/servidor/auditoria-cuentas.ts`). Cada persona cambia su propia contraseña desde **Ajustes → Mi cuenta** (cierra sus otras sesiones). El comando local `npm run usuarios` sigue disponible para crear cuentas, desactivar, activar y restablecer claves. Al actualizar una instalación existente, ejecuta `npm run auth:migrar` antes de iniciar la aplicación para convertir las cuentas existentes a rol `admin`. Si la instalación todavía tiene `estado.json` o `catalogo.json` antiguos, ejecuta primero `npm run migrar:sqlite`.

Abre [http://127.0.0.1:3000](http://127.0.0.1:3000). Los scripts de desarrollo y producción escuchan solo en `127.0.0.1`.

En **Cotizar**, el detalle del pedido aparece primero y la página se desplaza completa en escritorio. El asistente puede contraerse; el total y la acción principal permanecen visibles abajo. **Agregar producto** busca en el catálogo sin usar IA y permite iniciar un borrador o ampliar el pedido. Cliente, despacho, observaciones y detalles de cada producto se abren al necesitarlos; los productos pendientes muestran su editor y el importe se identifica como total parcial. Los campos de ancho, alto y largo muestran metros y aceptan «0,80», «0.80», «80», «80 cm» o «2100 mm» (`leerMedida`, `src/app/formato.ts`). En móvil, las vistas **Pedido** y **Cotización** conservan la conversación y el texto escrito al cambiar.

Si no tienes Chrome/Chromium instalado, ejecuta `npx playwright install chromium`. El generador detecta Chrome en macOS y Chromium/Chrome en Linux; puedes indicar otro ejecutable con `CHROMIUM_PATH`. Si npm arroja `Cannot read properties of null (reading 'edgesOut')`, agrega `legacy-peer-deps=true` a `.npmrc` y vuelve a instalar.

- **Accesorios de hasta 6 m:** el largo de marcos, molduras y piezas T va de 0,3 a 6 m («3,6», «360» o «3600 mm»); las puertas siguen entre 0,3 y 3 m.
- **Guía «Cómo funciona»** en `/ayuda`, enlazada desde el menú de la cuenta y desde la pantalla vacía del cotizador.
- **Sección «Avanzado»** plegada, con una advertencia: en **Ajustes → Asistente** (modelo, respaldo, clave y «Probar modelo»; se abre sola si falta la clave), en **Ajustes → Precios y descuentos** (IVA y ganancia por categoría; guardar con un error adentro la abre) y en **Catálogo → Nombres y alias** (vista técnica en JSON). ## Despliegue con Docker

La guía completa del servidor (instalación, proxy HTTPS, primera cuenta, actualizar, respaldo diario, restaurar y estado) está en [docker/LEEME.md](docker/LEEME.md); la versión para quien no programa, en el [manual operativo](docs/manual-operativo.md).

Verificar y desplegar son pasos separados (`scripts/deploy.mjs`):

| Comando              | Qué hace                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run verificar`  | Tipos, lint, `npm test` (Vitest y Playwright, con la planilla privada) y `npm run evaluar:regresion` (llama a la IA con el modelo de Ajustes de la base local; cuesta unos centavos de dólar). No empaqueta ni sube nada.                                                                                                                                                                                                                                                                |
| `npm run deploy`     | Verifica y sube la entrega por SSH a `chome:/srv/cotizador-neltume`. En el servidor toma un lock, revisa disco, RAM y carga, **respalda los datos** si el cotizador ya corre (si el respaldo falla, no actualiza nada), conserva el `.env` y las carpetas `respaldos*`, `compose.override.yaml`, `cron/` y `.version-anterior/`, sincroniza el resto y ejecuta `docker compose up -d --build --wait`. En el primer despliegue crea el `.env` con un secreto nuevo y `NELTUME_PORT=3010`. |
| `npm run deploy:zip` | Verifica y genera `deploy/neltume-cotizador-<fecha>.zip` con el código, Dockerfile, Compose, los scripts del servidor, `docs/manual-operativo.md` y un `.env` con un secreto nuevo y `NELTUME_PORT=3000` (otro con `--port N`). La instalación parte con base vacía, sin trasladar datos ni credenciales locales.                                                                                                                                                                        |

Opciones de ambos: `--url https://cotizador.tudominio.cl` deja configurados `BETTER_AUTH_URL` y `NELTUME_HOSTS`; `--sin-ia` omite solo la evaluación de la IA; `--solo-verificar` verifica y no empaqueta (es lo que hace `npm run verificar`); `--sin-verificar` empaqueta o sube **sin verificar**, solo para una entrega que ya se verificó en otro equipo (avisa en pantalla); `--forzar` omite el chequeo de recursos del servidor, pero no el lock.

**Instalación nueva con el ZIP:** descomprímelo en el servidor, completa `BETTER_AUTH_URL` y `NELTUME_HOSTS` en `.env` si no usaste `--url`, configura el proxy HTTPS y `NELTUME_IP_HEADER`, y ejecuta `docker compose up -d`. Docker compila la app para el servidor, incluye Chromium y conserva SQLite, PDF y respaldos en volúmenes. El contenedor se niega a arrancar, con un mensaje en el registro, si `BETTER_AUTH_SECRET` falta o tiene menos de 32 caracteres, si `BETTER_AUTH_URL` no empieza con `https://` o si `NELTUME_IP_HEADER` tiene un valor desconocido (`docker/iniciar.sh`). Crea la primera cuenta desde la página de inicio de sesión con el código del registro (`docker compose logs cotizador | grep -A2 "Código de un solo uso"`) o por terminal con `docker compose exec cotizador npm run usuarios -- crear admin@tudominio.cl Admin`.

**Actualizar con un ZIP, en el servidor y sin el equipo de desarrollo:** `sh scripts/actualizar.sh /ruta/neltume-cotizador-<fecha>.zip` revisa la entrega, respalda los datos con `npm run respaldar` (si falla, no actualiza), guarda el código actual en `.version-anterior/`, copia la versión nueva sin tocar `.env`, `respaldos*`, `compose.override.yaml` ni `cron/`, construye la imagen (si falla, deja los archivos como estaban y sigue la versión anterior) e inicia la nueva esperando el chequeo de salud. Si no pasa, `sh scripts/actualizar.sh --volver` detiene el cotizador, restaura los datos del respaldo tomado antes de actualizar (lo posterior queda apartado, no se borra), reinstala el código anterior y lo inicia; pide escribir `VOLVER` (`--si` lo omite en un script). Una instalación anterior al script lo saca del ZIP nuevo y usa `--dir <carpeta>` (ver LEEME).

**Puertos:** dentro del contenedor la app escucha en el 3000 (`Dockerfile` y el healthcheck de `compose.yaml`). Compose la publica en `${NELTUME_BIND_IP:-127.0.0.1}:${NELTUME_PORT:-3000}` del servidor, y el proxy HTTPS debe apuntar ahí: 3000 con el ZIP (o el de `--port`), 3010 con `npm run deploy`. En desarrollo, `npm run dev` y `npm start` escuchan en `127.0.0.1:3000`.

### Modelo y clave de IA desde la interfaz

En **Ajustes**, dentro de la sección plegada «Avanzado» (con una advertencia), quien administra puede cambiar el modelo de CommandCode, guardar o quitar la clave API. Si la clave guardada ya no se puede descifrar (por ejemplo, porque cambió `BETTER_AUTH_SECRET`), Ajustes la muestra como ilegible y solo el chat responde 503 con «La clave de IA guardada ya no se puede leer. Vuelve a ingresarla en Ajustes.»; emitir, editar y registrar pagos siguen funcionando (`src/servidor/ajustes-ia.ts`). El modelo y la clave cifrada se guardan en la tabla `ajustes` de SQLite y aplican al chat y al alta de productos. La clave nunca se devuelve al navegador. `CMD_API_KEY` se mantiene como fallback compatible hasta que se guarde o quite una clave en Ajustes.

**Modelo de respaldo y prueba de modelos.** Bajo el modelo del asistente se elige un **modelo de respaldo** (por omisión Qwen 3.7 Flash; «Quitar respaldo» lo desactiva). El principal recomendado, y el predeterminado de una instalación nueva, es DeepSeek V4.1 Flash: en la evaluación del 2026-10-11 acertó 48/48 casos ×3 y 999 de 1.000 conversaciones de paridad sin el corrector por frase; el respaldo es de otro proveedor para no fallar junto con él. Ante un límite de uso o una caída momentánea, el modelo principal se reintenta una vez tras `CMD_REINTENTO_MS`; si sigue fallando, se agota su plazo, el modelo ya no existe (404) o la cuenta no tiene acceso, responde el de respaldo, siempre dentro de `CMD_PLAZO_TOTAL_MS`, y el registro del servidor anota el cambio (`[asistente] respaldo`, con el modelo de origen, el de destino y el código). Con una clave inválida no se intenta otro modelo. **Probar modelo** envía 5 pedidos de prueba (`src/asistente/prueba-modelo.ts`) al modelo elegido, sin respaldo y sin crear cotizaciones, y muestra si funciona con el cotizador, cuántos acierta y cuánto tarda; consume la cuota del modelo, por eso pide confirmación con su precio. Los errores de la IA llegan a la persona con su mensaje propio (límite, plazo, modelo rechazado), no con el genérico del servidor; el cuerpo de un 4xx del proveedor queda en el registro del servidor con la clave oculta. **Diagnóstico:** cada respuesta del chat trae `diagnostico` (modelo que respondió, si fue el respaldo, milisegundos), que la pestaña guarda en `sessionStorage` y **Ajustes → Asistente → Avanzado** muestra como «Última respuesta del chat», sin texto de la conversación.

CommandCode es el único proveedor. Se conserva `@anthropic-ai/sdk` como cliente para modelos Claude; los otros modelos usan Chat Completions. Ambos apuntan exclusivamente a CommandCode; no se llama directamente a Anthropic ni se usan su clave, token o URL de entorno. La selección del modelo no cambia el proveedor.

Los márgenes por categoría (en pantalla, «ganancia»), el IVA, la vigencia y el descuento máximo se configuran en **Ajustes** (valores iniciales en `MARGENES_INICIALES` y `REGLAS`, `src/negocio/precios.ts`: puertas sólidas Mara/Lenga 55 %, Pino Oregón 85 %, prepintadas 140 %, enchapadas Mara 75 %, marcos Pino Finger desnudos 100 % y enchapados 75 %; Raulí 55 %; marcos sólidos Pino Oregón 85 % y Lenga 55 %; marcos sólidos de otras maderas (Mara, Raulí), molduras y piezas T de madera sólida 25 %, igual que «otros»; IVA 19 %, 10 días hábiles y 50 %). El margen de los marcos sólidos en Mara o Raulí está por confirmar con Neltume ([docs/reglas-negocio.md](docs/reglas-negocio.md)). El descuento máximo no puede pasar de 50 % (`DESCUENTO_MAXIMO`, `src/negocio/limites.ts`). Cada cotización congela las reglas vigentes al crearse, y admite un margen especial por cotización o por línea. Los días hábiles excluyen fines de semana y feriados nacionales de Chile (fijos, Semana Santa, traslados de las leyes 19.668, 20.215, 20.299 y 20.983 y el solsticio de invierno); los decretados por única vez (leyes puntuales, elecciones) se sincronizan solos desde la fuente pública [boostr.cl](https://api.boostr.cl/holidays.json): al emitir, si los datos tienen más de un día, se refrescan el año en curso y el siguiente en segundo plano (la primera vez se espera hasta 3 s). Lo sincronizado se guarda en SQLite (esquema 8) y se suma a lo calculado, nunca lo reemplaza; sin conexión se usan las reglas y lo último guardado. `npm run feriados` sincroniza a pedido y muestra el estado. El descuento acepta hasta dos decimales con coma o punto («2,5» y «2.5» son 2,5 %). **Descuento por cantidad:** en **Ajustes → Precios y descuentos** se definen tramos «desde N puertas, X %» (N entero ≥ 2, 0 < X ≤ descuento máximo, umbrales distintos; sin tramos por omisión) que se congelan con el resto de las reglas al crear la cotización. Cuenta el total de puertas valorizadas (marcos, molduras, piezas T e ítems pendientes no cuentan) y rige el tramo de mayor umbral alcanzado; el descuento se recalcula solo cada vez que cambian las líneas y el panel explica por qué («14 puertas → 5 %», con el siguiente tramo). Editar el descuento lo fija a mano (respeta el máximo y no cambia con las líneas) hasta que se pulsa **Restaurar automático**; la actividad registra el tramo aplicado, el valor manual y la restauración. La IA nunca lo ve ni lo fija, y la nota de pedido sigue sin descuento. La tasa mostrada en pantalla y en los PDF se deriva de `REGLAS`. Redondeo, siempre a pesos enteros: unitario = round(precio fábrica × (1 + margen)); línea = cantidad × unitario; descuento = round(subtotal × %), calculado en centésimas de punto para que un medio peso exacto (2,3 % de $1.500 = $34,5) redondee a $35; neto = subtotal − descuento + flete (el flete es neto, lleva IVA y no recibe descuento); IVA = round(neto × IVA de las reglas, 0,19 por omisión). La nota de pedido usa ajuste cero, sin descuento ni flete, manteniendo el mismo redondeo por unidad.

### Despacho con Starken

Con **Starken** como transportista, el despacho de una cotización editable tiene el botón **Cotizar con Starken**: consulta la API de tarifas, muestra las opciones de agencia y domicilio (con IVA, neto y días de entrega) y, solo si la persona elige una, deja su valor **neto** (`costoTotal / 1,19`, en pesos enteros, siempre con el 19 % de Starken aunque el IVA de Ajustes sea otro: `netoDesdeIva`, `src/negocio/starken.ts`) como valor de despacho. El valor se sigue pudiendo escribir a mano, y la tarifa elegida (tipo de entrega, días, costo total y ciudad de destino) queda en la actividad de la cotización. Sin configuración, el botón aparece desactivado con «Starken no está configurado»; nunca es una página de error.

Las credenciales salen solo de variables de entorno del servidor (no se guardan en la base ni viajan al navegador):

| Variable                                                  | Uso                                                                                                                                                                                                                                     |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `STARKEN_URL`                                             | Base del servicio, sin el nombre del método: `…/starkenservices/rest`. Debe ser `https` (`http` solo hacia localhost o 127.0.0.1) y no se siguen redirecciones. Sin valor por omisión, para no apuntar a QA o producción por accidente. |
| `STARKEN_RUT`, `STARKEN_CLAVE`                            | Credenciales de la integración (cabeceras `rut` y `clave`).                                                                                                                                                                             |
| `STARKEN_CUENTA_CORRIENTE`, `STARKEN_CUENTA_CORRIENTE_DV` | Cuenta corriente y su dígito verificador. Si se usan, no se envía el RUT del cliente.                                                                                                                                                   |
| `STARKEN_RUT_CLIENTE`                                     | RUT del cliente en Starken; solo se usa sin cuenta corriente.                                                                                                                                                                           |

- **QA y producción** se distinguen únicamente por `STARKEN_URL` y las credenciales. QA: `https://restservices-qa.starken.cl/apiqa/starkenservices/rest`. La URL de producción y sus credenciales las entrega Starken al activar la cuenta (ver `documentacion_integracion_starken.pdf`, que **no está en el repositorio**: los PDF están en `.gitignore`, pídelo al equipo o a Starken); cámbialas y reinicia el servidor. No pruebes contra producción con datos reales de clientes sin acordarlo con Starken.
- Las listas de ciudades de origen y destino se descargan una vez cada 24 horas y quedan en memoria del servidor (si una descarga falla se usa la anterior). Cada consulta tiene un plazo de 10 s.
- El destino se busca por nombre de comuna o ciudad (sin tildes ni mayúsculas) en el destino del despacho y, si no, en la comuna del cliente. Si no se encuentra o hay varias ciudades posibles, la persona elige de una lista con búsqueda.
- **Ajustes → Despacho con Starken** (administración): ciudad de origen y, opcionalmente, el **peso por unidad (kg) y el espesor (cm)** medidos de cada familia (puertas, marcos, molduras, piezas T). Si una familia queda vacía, el peso y las medidas de cada producto se **estiman** (`src/negocio/peso-estimado.ts`):
  - Madera: densidad seca de referencia por madera (finger 500, Oregón y raulí 530, lenga 560, mara 600, prepintada 550 kg/m³; desconocida, 600).
  - Puertas: ancho × alto de la línea × 4,5 cm de espesor, por la fracción maciza según el tipo (bloque 90 %, panel 75 %, otras 85 %).
  - Marcos y piezas T: kit de dos jambas (largo + 5 %) y un dintel de 1 m, atados en sección cuadrada. La escuadría de los marcos sólidos está en pulgadas y se toma cepillada (90 % de la nominal); la de los sets Pino Finger (30X70, 30X90) está en milímetros y se toma tal cual.
  - Molduras: escuadría en cm × largo, atadas en sección cuadrada.
  - Embalaje: +1 cm de espesor y +4 cm de ancho y largo por unidad; cartón de 0,5 kg/m² para puertas y film de 0,2 kg/m² para el resto, más 0,2 kg fijos por unidad.
    El bulto indica «(estimado, con embalaje)» cuando usa la estimación. Los valores definidos en Ajustes se usan tal cual (peso embalado).
- El bulto se calcula con las líneas de la cotización: las unidades se apilan (espesores y pesos se suman; el ancho y el largo son los mayores) y se muestra para revisarlo, p. ej. «14 puertas · 3 líneas · total 84 × 90 × 240 cm, 420 kg» (espesor apilado × ancho × largo; cada línea de la cotización es un bulto). Con valores de Ajustes, marcos, molduras y piezas T se toman con sección cuadrada del espesor indicado.
- Cada tarifa llega firmada por el servidor (HMAC con una clave derivada de `BETTER_AUTH_SECRET`, ligada a la cotización, a la huella del pedido (productos, cantidades y medidas), al destino y a los datos de la tarifa; vale 15 minutos; `src/servidor/starken-firma.ts`) y la acción `editar` la verifica antes de aceptar el valor y de dejarlo en la actividad: el costo no se puede alterar desde el navegador, y si el pedido cambió después de cotizar, la tarifa ya no se aplica. Si cambias `BETTER_AUTH_SECRET`, las tarifas pendientes dejan de valer y hay que volver a cotizar.
- Pruebas: `NELTUME_STARKEN=fijo` (solo con `NELTUME_TEST_MODE=1`) reemplaza la API por un Starken simulado con ciudades y tarifas fijas, sin red. Los tests unitarios simulan `fetch`; ninguna prueba llama a la API real.

## Guion de cinco minutos

1. Escribe: «Cotiza 3 Huilo Huilo en oregón de 80 × 2,10 para Juan Pérez, Temuco».
2. Escribe: «Agrega marcos de oregón». El asistente pide escuadría, largo y cantidad. Si escribes solo «Agrega marcos», también pide la madera.
3. Responde: «3 de 2x4 de 2,1».
4. Revisa y pulsa **Emitir y generar PDF**. La primera cotización emitida será la **323**.
5. Escribe: «Se aprobó la 323». El asistente pide confirmar; al aceptar, la cotización queda aprobada y bloqueada. Registra un pago de al menos el 50 % del total y pulsa **Generar notas de pedido**: el diálogo pide la fábrica de cada ítem («Todo a Panguipulli» las asigna de una vez) y se descarga la nota **577** de Panguipulli.
6. Crea una nueva cotización y prueba «Una Molco de 1,60 de ancho»: muestra los anchos disponibles, sin inventar un producto.

Los datos del cliente son opcionales. Los ítems incompletos no suman y deben completarse o quitarse antes de emitir. Una cotización emitida puede descargarse siempre; modificarla crea un nuevo borrador (solo si hay cambios reales), conserva el PDF original y asigna un nuevo número cuando se emite. Una aprobada no admite cambios.

Solo se puede aprobar una cotización ya emitida, y tanto el botón como la aprobación pedida por chat exigen confirmación explícita. La aprobación se puede deshacer con **Deshacer aprobación** solo mientras no haya nota de pedido, pagos ni factura: la cotización vuelve a «Emitida» (acción `desaprobar`). «Nueva cotización» limpia la pantalla; el borrador se guarda recién cuando la IA responde al primer mensaje con un pedido o datos del cliente. Un saludo, una pregunta o una aprobación pedida desde una pantalla nueva se responden sin crear un borrador vacío, y ese intercambio se envía como contexto con el siguiente mensaje. Si la persona cancela la espera del primer mensaje y lo reenvía, el servidor reconoce el mismo mensaje (`nuevoId`) y abre la cotización que ya había creado en vez de duplicarla. Nombrar una cotización inexistente («la cotización 999») responde 404 sin tocar la cotización abierta.

### Ciclo de vida de una cotización

| Estado        | Significado                                                                                                                                                                           | Acciones                                                                                                                                                                                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `borrador`    | Sin número, editable.                                                                                                                                                                 | chat, `editar`, `quitar`, `emitir`, `duplicar`, `eliminar`                                                                                                                                                                                                                                        |
| `emitida`     | Tiene número y PDF; vence 10 días hábiles (lunes a viernes, sin feriados nacionales) después de emitirse, y el día de vencimiento todavía vale (`src/negocio/vigencia.ts`).           | chat o `editar` crean/reutilizan su revisión; `aprobar`, `anular`, `duplicar`, `regenerar_pdf` (solo administradoras)                                                                                                                                                                             |
| `aprobada`    | La aprobó el cliente; no admite cambios en sus ítems. La nota de pedido se genera con al menos 50 % pagado.                                                                           | `pago`, `anular_pago`, `asignar_fabricas` (hasta generar las notas), `generar_nota`, `operacion`, `retroceder_operacion`, `despacho`, `facturacion`, `cambiar_numero`, `desaprobar` (sin nota, pagos ni factura), `anular` (no si la operación está despachada o completada o si está facturada; las notas quedan marcadas como anuladas), `regenerar_pdf`, `duplicar` |
| `reemplazada` | Se emitió una revisión suya o se aprobó otra de la misma serie; no es aprobable ni editable.                                                                                          | `duplicar`                                                                                                                                                                                                                                                                                        |
| `anulada`     | Definitiva; conserva números y PDF. Sus documentos se descargan con la marca «ANULADA» (el PDF original queda intacto). Una revisión en borrador abierta queda como cotización nueva. | `duplicar`                                                                                                                                                                                                                                                                                        |

- Toda acción que modifica una cotización existente envía su `actualizada`; si no coincide, responde 409 y no cambia nada. Los mensajes del chat sobre una emitida se guardan en el historial sin cambiar su versión.
- Una emitida tiene a lo más una revisión abierta: los cambios siguientes se aplican sobre esa revisión. Emitir la revisión deja la original como `reemplazada`; aprobar una cotización deja `reemplazada` a las demás emitidas de su serie y bloquea emitir borradores de esa serie. Así nunca hay dos notas de pedido para un mismo pedido.
- Al emitir, los montos se recalculan con el catálogo vigente. Si cambió algún precio o el total, **no se emite**: el borrador se actualiza con los montos vigentes, queda registrado en su actividad y la respuesta es 409 `precios_cambiaron` con los avisos y el nuevo total; la interfaz los muestra y pide confirmar antes de emitir con la versión nueva. No se consume número. El diálogo de emisión muestra el total que se emitirá. Se guarda la versión del catálogo usada.
- Aprobar una cotización vencida exige confirmarlo explícitamente. La aprobación acepta dirección de despacho y medio de transporte, que se imprimen en la nota junto al giro del cliente. Si la cotización tenía una revisión en borrador, al aprobarla esa revisión queda como cotización nueva, con el aviso «La revisión en borrador quedó como cotización nueva.».
- La operación parte de la aprobación del cliente. Los pagos solo se registran en una cotización `aprobada` y se anulan (`anular_pago`, con motivo opcional y registro en la actividad) mientras la operación no llegue a «Lista para despacho»; el anticipo y el saldo pagado se recalculan al anular. Iniciar y terminar la producción exigen al menos 50 % pagado (el mismo umbral de la nota de pedido), así que anular el anticipo después de la nota frena la producción hasta volver a registrarlo; el diálogo de anulación lo advierte. Con la cotización aprobada y hasta registrar el despacho se editan los datos logísticos (`despacho`: transportista, destino, dirección y entrega comprometida); el valor del flete queda fijo desde la emisión y la nota de pedido conserva el despacho con que se generó. Registrar el despacho exige un transportista. **Volver al paso anterior** (`retroceder_operacion`, con un motivo que queda en la actividad) baja un paso de la operación, hasta «Nota de pedido generada», y recalcula el estado según lo pagado. Anular una cotización (también al marcarla rechazada por el cliente) deja su estado comercial en «rechazada»; no se puede anular con la operación despachada o completada ni con la facturación marcada como facturada (409; para anularla, primero hay que volver la facturación a pendiente). La facturación (`facturacion`: factura o boleta, N° y fecha) se marca a mano en una cotización aprobada, sin integración externa.
- Descuento (0–50 %; automático por cantidad de puertas o fijado a mano, con `descuentoAutomatico: true` en `editar` para volver al automático) y flete (neto) se editan por cotización y solo afectan a la cotización, nunca a la nota. Las líneas guardan el ancho, alto y escuadría pedidos, que se imprimen en ambos PDF.
- Duplicar copia ítems, cliente, descuento y flete en un borrador nuevo; si el descuento supera el máximo vigente, se recorta a ese máximo con un aviso.
- El número de una cotización lo asigna el correlativo. Solo una cuenta administradora puede elegirlo a mano al emitir: debe ser mayor que el último usado o reservado y no superarlo en más de 1.000, y los números saltados no se vuelven a usar (`reservarCotizacion`, `src/servidor/almacen.ts`). Después de emitir, una cuenta administradora puede cambiar el número de la cotización o de una de sus notas desde su documento («Cambiar N°») o por chat, con confirmación (`cambiar_numero`): debe estar libre en su serie, se vuelve a generar el PDF con un nombre nuevo (al cambiar el de la cotización, también los de sus notas, que la nombran) y el anterior se borra.
- **Notas por fábrica.** Cada ítem lleva la fábrica que lo hace (`SolicitudItem.fabrica`), que elige quien cotiza: en el seguimiento, al generar las notas o por chat (la herramienta `asignar_fabricas` de la IA; el servidor anula una fábrica que el mensaje no nombra). `generar_nota` genera una nota por fábrica con sus ítems y su correlativo, todas en una sola emisión; la producción se marca por nota (`operacion` con `fabrica`) y el pedido sigue cuando terminan todas (esquema 25).
- Si el PDF de una cotización o de una nota ya no está en el servidor (por ejemplo, tras restaurar sin la carpeta `pdf`), al descargarlo una cuenta administradora puede **Regenerar PDF** (`regenerar_pdf`): se reconstruye desde el HTML guardado al emitir (tabla `documentos_snapshot`) o, en documentos anteriores al esquema 22, desde los importes guardados, con un aviso. Nunca sobrescribe un archivo existente y deja «PDF regenerado» en la actividad.
- Cada cotización guarda su registro de **Actividad** (tabla `eventos`, esquema 7): creación, revisiones, cambios con su detalle, emisión, aprobación, reemplazo y anulación, con fecha y cuenta.
- Se registra quién creó, emitió, aprobó y anuló cada cotización (nombre de la cuenta). El RUT se normaliza a «12.345.678-5» si su dígito verificador es válido; si no, se conserva con un aviso.

El contrato completo de `/api/accion` y `/api/catalogo` está descrito en los tipos de `src/servidor/servicio.ts`, `src/negocio/estado.ts` y en los esquemas Zod de cada ruta. El listado (`GET /api/accion`) devuelve páginas de resúmenes con búsqueda por N°, cliente, RUT, teléfono, comuna, proyecto, modelo y madera, filtros `vencenPronto` (emitidas que vencen en los próximos 7 días) y `saldoPendiente` (aprobadas con pagos por completar), ordenadas, agrupadas y filtradas por una sola fecha de referencia (anulación, aprobación, emisión o, en un borrador, su última edición); filtros `comercial` y `operativo` (seguimiento y paso de la operación; admiten varios) y `vendedora` (quien la creó; `GET /api/accion?vendedoras=1` da la lista); con `formato=csv` descarga el listado filtrado para Excel, con pagado, saldo, operación y facturación, hasta 5.000 filas por archivo (`MAX_EXPORTACION`, `src/servidor/exportar.ts`): si hay más, responde 409 `exportacion_por_partes` con el total y las partes, y `parte=N` entrega cada tramo en el orden del historial (nunca corta en silencio). `GET /api/accion?papelera=1&q=&pagina=` lista los borradores de la papelera, paginados y con búsqueda en el servidor, junto con `plazoDias` (30, `DIAS_PAPELERA`); se restauran con `restaurar_borrador`, que conserva el destino, el valor del despacho y la actividad. `GET /api/accion?numeracion=1` (solo administradoras) da el último número usado y el tope para el número manual. `GET /api/accion?id=` devuelve la cotización completa y su actividad. `GET /api/catalogo?q=&familia=` consulta el catálogo con el precio unitario de la cotización; en la interfaz está en **Catálogo → Consultar**.

## Separación de responsabilidades

- `src/catalogo/xlsx.ts`: lectura selectiva del XML de XLSX con `fflate` y `saxes`. No construye un Workbook que materialice costos; solo decodifica valores y fórmulas de celdas permitidas.
- `src/catalogo/importar.ts`: tablas de `Categorias`, normalización, hipótesis de corrección, duplicados, descripción, SHA-256, catálogo y reporte.
- `src/catalogo/enchapadas.ts` y `src/catalogo/planilla.ts`: lectura de la planilla de enchapadas, prepintadas y marcos Pino Finger (bloques por hoja, solo columnas B a D) y detección de cuál de las dos planillas es un libro, por la forma de sus hojas.
- `src/servidor/importacion-catalogo.ts`: vista previa de una importación, comparada solo con los productos de su planilla.
- `config/catalogo.json`: maderas, códigos para SKU, alias y familias especiales, guardados en SQLite junto con cada importación.
- `src/catalogo/resolver.ts`: modelos, alias, medidas, rangos y rechazos determinísticos.
- `src/negocio/precios.ts`: precios, redondeo, IVA y validaciones.
- `src/asistente/llm.ts`: adaptador de CommandCode y proyección explícita del contexto sin precios. Usa el [Provider API de CommandCode](https://commandcode.ai/docs/provider) con `/messages` para Claude y `/chat/completions` para los otros modelos de chat, con una única herramienta por turno y validación estricta con Zod. Del catálogo solo se envía un resumen por modelo (`src/catalogo/mapa.ts`: familia, maderas y medidas); no se reenvían montos, códigos, historial de precios ni respuestas de cálculo. Una respuesta con formato inválido o índices inexistentes se reintenta una vez, indicándole al modelo qué corregir.
- `src/servidor/alta-catalogo.ts`: conversación de alta de producto, extracción de atributos, validación del precio explícito y confirmación transaccional.
- `src/app/api/catalogo/route.ts`: endpoint interno para proponer y confirmar productos nuevos.
- `src/asistente/preguntas.ts`: preguntas determinísticas a partir de los rechazos, sin segunda llamada al modelo.
- `src/negocio/pendientes.ts`: las mismas preguntas en forma estructurada (campo, ítems y opciones válidas) para responderlas en la interfaz con una edición directa.
- `src/asistente/anclaje.ts`: verificación de que cada cantidad o medida nueva que propone la IA esté escrita en la conversación.
- `src/negocio/vigencia.ts` y `src/negocio/cliente.ts`: días hábiles y vencimiento; saneamiento del cliente y RUT.
- `src/servidor/almacen.ts`: unidad de trabajo por cotización, reserva de correlativos (`UPDATE … RETURNING`), listado y búsqueda.
- `src/servidor/errores.ts`: errores con estado HTTP y `codigo` estable (400, 404, 409, 503).
- `src/app/`: interfaz. Tipografía Host Grotesk (interfaz) y Newsreader (títulos y totales), servidas con `next/font` desde `src/servidor/pdf-recursos/fuentes/`. El seguimiento y el historial muestran el avance del pedido como una línea de ocho pasos (`src/negocio/pasos.ts`, `linea-pasos.tsx`); las líneas de la cotización y el catálogo llevan el dibujo del modelo (`/api/dibujo/<modelo>`, `dibujo-modelo.tsx`). El ingreso (`src/app/login/`) muestra la puerta Neltume en 3D con three.js (`escena-puerta.ts`, modelo en `public/3d/`): solo con WebGL y sin «reducir movimiento»; si no, una foto fija.
- `src/servidor/`: flujo, persistencia, plantillas HTML y PDF A4 con Playwright. Los PDF usan Newsreader y Host Grotesk y un dibujo de línea de cada modelo de puerta (en la nota de pedido, con las cotas de la medida pedida); fuentes y dibujos viven en `src/servidor/pdf-recursos/` y se incrustan al imprimir, sin red. Un modelo 3D nuevo en `modelos-3d/puertas` se dibuja con `scripts/dibujos/generar.sh` (Blender); los modelos sin 3D (Huilo Huilo, Los Ríos, Los Lagos, Calafquén, Cochamó, Enco, Ensenada, Futaleufú, Fuy, Palena, Petrohué, Ranco, Rupanco y Yelcho) se dibujan a mano con `scripts/dibujos/dibujos-2d.py` (referencia: las fotos de la planilla de enchapadas y de puertasneltume.cl); un modelo sin dibujo usa el esquema genérico de puerta.
- `src/servidor/autenticacion.ts`: sesiones y verificación de acceso con Better Auth sobre la misma base SQLite.
- `scripts/usuarios.ts`: alta, desactivación, activación y restablecimiento de cuentas desde terminal.
- `tests/pantallas.ss.ts` (`npm run ss`): captura cada pantalla y cada estado de una cotización, en escritorio (1920 × 1080) y teléfono (390 × 844), con la base aislada de la E2E; quedan en `capturas/` (`SS_COMPLETA=1` captura la página entera).
- `scripts/notas.ts` (`npm run notas`): próximo N° de nota de pedido de cada fábrica (Panguipulli y Santiago numeran por separado), fijarlo y asignar fábrica a las notas anteriores a la separación.
- `src/servidor/primer-arranque.ts` y `src/app/api/primer-arranque/`: código de un solo uso y creación de la primera cuenta desde la página de inicio de sesión.
- `src/servidor/auditoria-cuentas.ts`: registro de cambios de cuentas (tabla `auditoria_cuentas`).
- `src/negocio/limites.ts`: límites comerciales en un solo lugar (rango de medidas por familia, margen, ajuste, descuento máximo y anticipo).
- `src/servidor/items-vigentes.ts`: resuelve los ítems contra el catálogo y deja pendiente, con su pregunta, un precio o un descuento fuera de regla, venga del detalle, del chat o de deshacer.
- `src/asistente/frases.ts`: normalización compartida de las frases del pedido para el anclaje y la cobertura («80 x 200» = «80x200»).
- `src/servidor/clientes.ts` y `src/app/api/clientes/`: clientes de cotizaciones anteriores para autocompletar.
- `src/app/api/salud/`: estado del sistema (ver «Estado del sistema»).
- `scripts/restaurar.ts` y `scripts/lib/restauracion.ts`: restauración de un respaldo; `scripts/respaldo-diario.sh` y `scripts/actualizar.sh`: tareas del servidor con Docker.
- `src/app/`: pantalla y [Route Handlers de Next.js](https://nextjs.org/docs/app/api-reference/file-conventions/route).

El LLM devuelve solo los cambios pedidos (agregar, editar por índice, quitar y datos del cliente), tanto en una cotización nueva como al modificar una anterior: así no puede alterar un ítem que el mensaje no menciona. Cada ítem guarda la frase del pedido de la que salió (`fuente`, esquema 16), que el panel muestra junto al ítem. Toda cantidad o medida nueva debe aparecer en la conversación, en dígitos o, para cantidades, en palabras («tres», «media docena»); si no aparece, queda pendiente con un aviso en vez de cotizarse. Los ítems pendientes se completan con botones en el chat y en el panel, que guardan el dato sin volver a consultar a la IA; las preguntas iguales de varios ítems se agrupan y se sugiere el valor de otro ítem del pedido («Como el ítem 1»), sin aplicarlo solo. El servidor puede resolver una referencia por número, nombre, proyecto o comuna con búsqueda local insensible a tildes. Si encuentra varias, muestra opciones sin modificarlas. En el flujo de cotización, los montos siempre se calculan en el servidor y no se envían al LLM. **Lo que sí viaja a CommandCode en cada mensaje** (`contextoSeguro`, `src/asistente/llm.ts`): el mensaje, los últimos 6 turnos del chat (recortados), los modelos y maderas del catálogo con sus alias y, del borrador, cada ítem con su modelo, madera, medidas, cantidad, tipo de medida, **descripción y observaciones escritas por la persona** y la frase de origen, más **los datos del cliente** (nombre, RUT, giro, teléfono, dirección, comuna y proyecto). Sin precios, costos ni totales. Conviene no escribir en las observaciones de un ítem nada que no deba salir del servidor. En el alta de producto, la IA extrae solo atributos; el servidor interpreta el precio neto desde el texto original y exige confirmación. La consulta a la IA se hace fuera del bloqueo del estado: si la cotización cambió mientras tanto, la respuesta no se aplica y se pide reenviar el mensaje. Una salida inválida no modifica las solicitudes, el cliente ni los montos y responde «No entendí, ¿puedes reformularlo?». Una cantidad no entera o fuera de 1–10.000 queda pendiente con un aviso. Los cambios reales se detectan comparando los ítems resueltos (código, cantidad y medidas pedidas) y el cliente normalizado, no el texto del modelo; la respuesta incluye `cambios` (ítems agregados, quitados y modificados) para mostrar la diferencia.

**Modo del anclaje por frase.** El cliente de IA usa por omisión el modo «avisar» (`ModoAnclaje` en `src/asistente/llm.ts`): la lectura de la IA se conserva y, si la frase del pedido parece decir otra cosa, el chat lo avisa en un solo aviso por ítem («Revisa el ítem 1 (MOLCO): anoté la cantidad 2, pero tu mensaje parece decir 3.»). En ese modo no hay respuesta directa sin IA, reordenamiento del flete ni reintento por productos omitidos; si la IA responde con texto a un pedido, el chat avisa que no agregó productos. Las cifras, los nombres, los montos y el flete se siguen anclando a lo escrito. El modo «corregir», descrito a continuación, se retira después de observar «avisar» en uso; mientras, sirve para comparar con `--anclaje`. Cada mensaje del chat deja en el registro del servidor una línea `[asistente]` con la herramienta usada, los avisos por tipo y el tiempo, sin el texto.

Para que una misma frase dé siempre la misma lectura, la IA se consulta con `temperature` 0; si un modelo no acepta esa opción (o `tool_choice` forzado), se repite sin ella. Además del anclaje de cifras y nombres, cada ítem se revisa contra su propia frase (`anclarFrases` en `src/asistente/anclaje.ts`): la madera, el modelo, las medidas y la cantidad no pueden venir de la frase de otro ítem («futrono pino oregón … y Los Lagos raulí» no deja la Futrono en raulí), y lo que la frase dice sin ambigüedad corrige a la IA («marcos mara» no es Mara enchapada, «media docena» son 6, «1230 x 2600 mm» son 1,23 × 2,6 m). Una frase sin modelo («… y 2 de 70x210»), «otra igual» o «con su marco» heredan lo que no dicen. Si la respuesta deja fuera productos del mensaje, o pregunta por el chat lo que debía registrar como pendiente, la IA recibe una corrección y se le pide una vez más (`src/asistente/cobertura.ts`); si aun así falta algo, el chat avisa «No registré: «…»». Si registró solo el flete y ningún producto (pasaba en pedidos largos con despacho), el reintento va sin la línea del flete y conserva el flete y el cliente de la primera respuesta. Para que eso pase menos, la IA recibe las líneas del flete al final del mensaje (las líneas no cambian). Un mensaje que solo responde la pregunta pendiente («lenga», «son 3», «de 210 de alto», «6 pulgadas») se aplica sin consultar a la IA, igual que los botones (`src/asistente/respuesta-directa.ts`). El catálogo que ve la IA separa las secciones de cada grupo de maderas (marcos sólidos 2x4–2x8, marcos finger 30x70/30x90).

Ninguna corrección del servidor pasa en silencio: si la frase corrige el modelo, la madera, la sección, la cantidad o una medida que propuso la IA, el chat lo avisa («Revisa el ítem 4 (HUILO HUILO): el asistente leyó la madera «MARA ENCHAPADA», pero tu pedido dice «MARA»; usé «MARA».»). También avisa las palabras que no reconoce entre el modelo y la madera o justo después de ella («No reconocí «barnizada» en el ítem 2…»), que suelen indicar un alias que falta en la configuración del catálogo. Si la IA cambia la palabra que ocupa el lugar del modelo por otro modelo del catálogo («3 Pillo oregón 80×210» leído como una pilastra), se conserva lo escrito y el sistema pregunta si es el modelo que se le parece; una sección que la conversación no dice se descarta. Los alias de madera que trae el código (por ejemplo «encha mara», «enchap en mara») se suman a la configuración guardada al cargarla, igual que los de modelo.

**Precios escritos y pedidos especiales.** Además del flete, la IA registra el precio que la persona escribe para un producto («a $450.000 + IVA», «en 450 mil c/u»). El servidor busca el monto primero en la línea del mensaje que contiene la frase de ese ítem (así no toma el precio de otro producto ni el del flete) y, solo si esa frase no se ubica en el mensaje, en lo que escribió la persona en la conversación, nunca en los textos del asistente (`preciosEscritos`, `src/servidor/servicio.ts`; `montoEscrito`, `src/asistente/montos.ts`). Lo guarda neto («IVA incluido» se descuenta; si no lo dice, lo toma neto y avisa) y lee «$350.00» como $350.000, porque en pesos no hay centavos; un monto dudoso como «$350.50» no se aplica. Si el precio escrito es el total de varias unidades, no se aplica y el chat avisa «Escribiste un precio total para el ítem N; indica el valor por unidad.». Si el producto está en el catálogo, usa ese precio y avisa cuál era el de catálogo. Si no existe (modelo, madera o medida fuera del catálogo), la línea pasa a ser un pedido especial (`ESPECIAL`) con el nombre, la madera, las medidas y el precio pedidos. Sin precio queda pendiente: el chat explica cómo cotizarlo y el panel ofrece «Cotizar como especial», que solo pide el precio neto (en pantalla, «sin IVA»). Una puerta a menos de 5 cm bajo la menor medida de su madera se cotiza con esa medida (0,69 → 0,70); desde 5 cm menos, pregunta. La familia de un especial sale de su modelo o, si el catálogo no lo conoce, de su nombre («marco», «guardapolvo») o de su forma: solo una puerta cuenta para el descuento por cantidad. En la nota de pedido, una línea especial va a su **costo de fábrica** si se indicó en el detalle (campo opcional); sin él, va «Por definir» y no suma al total. Nunca va con el precio de venta. Un precio escrito a mano para un producto del catálogo debe quedar entre −50 % y 500 % sobre su costo: al editarlo en el detalle, un valor fuera de rango se rechaza con el rango en pesos; si queda fuera por otra vía (el chat, deshacer o una reimportación que cambió el costo), el ítem queda pendiente con esa pregunta y no suma hasta corregirlo o quitarlo (`src/servidor/items-vigentes.ts`). En la cotización, «Consultar valor despacho.» solo se imprime si no hay línea de flete.

Referencias: solo cuentan «cotización 450», «cotización N° 450», «nro de cotización 450» o «la 450» fuera de una dirección; un «#450» o «N° 450» suelto (p. ej. «Los Carrera #450») no es una referencia. Entre varias coincidencias por nombre se prefiere la conversación abierta. Medidas: hasta 10 se interpretan en metros, hasta 300 en centímetros y hasta 3000 en milímetros; en el largo de marcos, molduras y piezas T, hasta 600 cm y 6000 mm. Fuera de 0,3–3 m en una puerta, o de 0,3–6 m en el largo de un accesorio, el asistente pregunta (`rangoMedidas`, `src/negocio/limites.ts`; `metros`, `src/catalogo/resolver.ts`). Si dos productos manuales cubren el mismo ancho, pregunta cuál en vez de elegir.

### Agregar modelos y maderas

El catálogo se mantiene desde la aplicación (**Catálogo → Importar**, **Agregar producto**, **Gestionar catálogo** y **Nombres y alias**) o, por terminal, con la planilla y `config/catalogo.json`. La configuración vigente (maderas, alias y familias) vive en la base y se edita en **Nombres y alias**; en Docker, `config/catalogo.json` va dentro de la imagen y editarlo en el servidor no cambia nada. `npm run importar` combina las dos y manda la de la base: un modelo, madera o familia que la base ya tiene queda como está en **Nombres y alias**, y del archivo solo se suma lo que la base no tiene. En una instalación con datos, los alias de un modelo existente se cambian en **Nombres y alias**, no en el archivo.

1. Para agregar un modelo de puerta, agrega su nombre y código en `Categorias!O:P` y sus productos en la hoja `Precio`. Se admiten filas de categorías hasta la 500. Los nombres de modelo y madera se normalizan sin distinguir mayúsculas ni tildes.
2. Para una madera nueva, agrega su nombre en `Categorias!G`, sus productos en `Precio!G` y una entrada en `config/catalogo.json` con `nombre`, `codigo` único y los `alias` que se usan al pedirla. El código se usa en los SKU importados.
3. Para clasificar un modelo como marco, piezas T o moldura, agrega su familia en `familiasPorModelo`. Los modelos sin entrada se consideran puertas. Las familias disponibles son `PUERTA`, `MARCO`, `PIEZAS_T` y `MOLDURA`.
4. Si la gente usa nombres alternativos para un modelo, agrégalos en `aliasModelos`, bajo el nombre canónico. Si un nombre solo se parece y puede ser otra cosa (por ejemplo «Pillo»), agrégalo en `aliasPosiblesModelos`: el cotizador no lo sustituye ni se lo envía a la IA como alias; deja el ítem pendiente y pregunta «¿Te refieres a…?» hasta que se confirme el modelo con el botón «Confirmar» del panel. Un modelo real del catálogo siempre gana sobre cualquier alias.
5. Importa la planilla actualizada con `npm run importar -- ruta.xlsx` (en Docker, con la receta de `docker/LEEME.md`, que monta la planilla de solo lectura). La operación reemplaza productos y configuración juntos en una transacción; si la validación falla, ambos quedan como estaban. El reporte (`data/reporte-importacion.md`) se escribe antes de guardar, así que queda también cuando la importación se rechaza; si algo falla después de guardar, el mensaje dice que el catálogo sí quedó guardado. Las cotizaciones existentes conservan sus snapshots. La importación se rechaza completa si más de 5 filas (y más del 1 %) de `Precio` tienen datos incompletos o un precio inválido, si un mismo producto aparece dos veces con precios distintos (una repetición idéntica solo se reporta) o si la planilla trae menos del 90 % de los productos del catálogo actual; en este último caso, si la reducción es intencional, repite con `npm run importar -- ruta.xlsx --forzar`.

### Planillas por origen: puertas sólidas y enchapadas

El catálogo se arma con dos planillas, cada una un _origen_ de productos:

- **Planilla de puertas sólidas** (`COTIZADOR_2026.xlsx`: hojas `Precio`, `Categorias` y `Cotización`).
- **Planilla de enchapadas, prepintadas y marcos finger** (`VALORES PUERTAS ENCHAPADAS…xlsx`): una hoja por modelo con bloques «<MODELO> PREPINTADA» y «<MODELO> ENCHAPE EN MARA» (rango de altura × ancho → costo) y la hoja de marcos con sets Pino Finger desnudos y enchapados en Mara. Solo se leen las columnas de medida y **costo «+ IVA»** (neto de fábrica); venta, margen y descuento especial no se leen: el precio sale del costo por el margen de cada categoría (prepintadas 140 %, enchapadas en Mara 75 %, marcos finger desnudos 100 % y enchapados 75 %). Los bloques que no son de estas terminaciones (por ejemplo los sets de endolado MDF) no se importan y quedan en las incidencias. Los productos son las maderas `PREPINTADA`, `MARA ENCHAPADA`, `PINO FINGER` y `PINO FINGER ENCHAPADO MARA`, con códigos estables como `HUIL-EM-085-240` (modelo, madera, ancho en cm y alto máximo en cm) y `MARC-PF-30X70-220` (escuadría en mm y largo en cm).

En **Catálogo → Importar** el formato se reconoce solo (un `.xlsx` con contraseña de apertura o un `.xls` antiguo se rechazan con un mensaje que lo dice) y la vista previa compara únicamente con los productos de esa planilla, separando los que solo cambiaron la descripción; la otra y los productos agregados a mano no se modifican. El control del 90 % de productos conservados es por planilla, y un código o producto repetido en la otra planilla se rechaza. La versión del catálogo cambia con cada importación de cualquiera de las dos. `npm run importar -- ruta.xlsx` acepta ambas (el reporte de las enchapadas va a `data/reporte-importacion-enchapadas.md`). Al importar las enchapadas, las maderas nuevas se suman a la configuración guardada si no estaban. Un precio editado a mano en un producto de la planilla se reemplaza por el de la planilla en la siguiente importación de esa planilla, y la vista previa lo avisa. La vista previa separa los productos a los que solo les cambió el texto de la descripción («Formato de descripción actualizado», plegado): no cuentan como modificados. Después de importar, **Volver a la planilla anterior** deja esa planilla como estaba antes de la importación, incluidos los precios editados a mano y su marca (la próxima vista previa los vuelve a avisar), siempre que nadie haya cambiado el catálogo entretanto; no toca la otra planilla ni los productos agregados a mano, y la importación deshecha queda como copia, a la que se puede volver con el mismo botón (`restaurarImportacion`, `src/servidor/repositorio-catalogo.ts`). El botón sigue disponible al recargar o al cambiar de sección: la pantalla lo consulta con `GET /api/catalogo/importar`. Un Excel con contraseña de apertura o un `.xls` antiguo se rechazan con un mensaje que dice cómo guardarlo.

Ejemplo de entrada para una madera: `{ "nombre": "ROBLE", "codigo": "RB", "alias": ["ROBLE AMERICANO"] }`. Configuración y catálogo aplicados quedan en la base SQLite; el JSON es la fuente editable para la próxima importación. El cambio de esquema añade esta configuración de forma compatible al abrir una base existente.

En la aplicación también puedes abrir **Catálogo → Agregar producto** y describirlo en lenguaje natural. El precio que se ingresa es el neto base (en pantalla, «Precio base sin IVA»): la cotización le suma el margen de su categoría, como a los productos de la planilla, y la vista previa muestra ambos valores. Indica familia, modelo, madera, medidas y precio neto unitario; la IA pregunta los datos que falten. El precio debe aparecer explícitamente en el texto. El servidor genera un código, presenta una vista previa y guarda el producto solo después de tu confirmación. El precio acepta «45.990», «45,990» (miles), «45,99», «1.5 mil», «3 mil quinientos» y «1,2 millones»; «+ IVA» o «neto» se toman como neto, y «IVA incluido», «con IVA» o «bruto» se convierten a neto dividiendo por 1,19 con un aviso en la vista previa. Si el precio está a más de 3 veces (o menos de un tercio) de la mediana del mismo modelo o familia, la vista previa lo advierte. Se rechaza un rango de ancho que se cruce con otro del mismo modelo, madera y alto. Cada propuesta pendiente pertenece a la cuenta que la inició. Al confirmar, el producto queda disponible en **Catálogo → Consultar** junto con los de la planilla. Estos productos permanecen en SQLite y sobreviven a futuras importaciones de Excel; si la planilla contiene el mismo código o combinación de atributos, se rechaza la importación completa. Al eliminar uno, va a la papelera: **Catálogo → Gestionar catálogo → Productos eliminados** lo restaura tal como estaba, con quién lo agregó y su fecha de alta, si su código sigue libre. `npm run limpiar-borradores -- --confirmar` vacía de la papelera lo eliminado hace más de `--dias` días.

Para actualizar una instalación que todavía tiene `catalogo.json` o `estado.json`, detén el servidor y ejecuta `npm run migrar:sqlite`. El comando valida una base temporal, conserva los JSON en un respaldo fechado y no sobrescribe una base SQLite existente que no haya sido migrada. No inicializa una base vacía ignorando JSON anteriores. En una instalación nueva, `npm run importar -- datos-privados/COTIZADOR_2026.xlsx` carga catálogo y configuración directamente en SQLite.

Los cambios se confirman con transacciones SQLite y cada operación lee y escribe solo las cotizaciones que toca; las lecturas de varias tablas se hacen dentro de una transacción. El bloqueo en `data/.estado.lock` serializa las escrituras. El correlativo se reserva (`UPDATE … RETURNING`) antes de generar cada documento; el PDF se genera fuera del bloqueo, con un plazo total de 30 s, y al terminar se vuelve a tomar el bloqueo para confirmar solo si la cotización no cambió. Un fallo puede dejar un salto, nunca reutilizar un número, y un PDF existente nunca se sobrescribe (`data/pdf` con permisos 0700 y archivos 0600). Una fila dañada se omite del listado y se registra en el servidor sin afectar a las demás. El esquema 6 (estados «reemplazada» y «anulada», autoría, vigencia, descuento, flete, giro, medidas pedidas y despacho) se aplica solo al abrir una base anterior; las filas existentes quedan con valores nulos o cero y las originales cuya revisión ya se había emitido pasan a «reemplazada». El esquema 15 agrega `descuento_manual` (qué cotizaciones tienen el descuento fijado a mano): las que ya tenían descuento quedan como manuales y las demás como automáticas; los tramos viven en las reglas congeladas (`reglas_json`), así que las anteriores no los tienen. Las notas y cotizaciones conservan sus snapshots de precios aunque el catálogo cambie. No borres la base para reiniciar los correlativos.

### Respaldo y restauración

`npm run respaldar` copia en caliente, sin detener el servidor, la base (API de respaldo de SQLite, verificada con `integrity_check`), los PDF emitidos, las referencias del cliente (`data/referencias/`) y `config/catalogo.json` a `respaldos/cotizador-<fecha>/`, y conserva los 30 más recientes. `--destino ruta` (o `NELTUME_RESPALDO_DIR`) cambia la carpeta —conviene otro disco o una carpeta sincronizada— y `--conservar N` la cantidad. Con `--json` informa el resultado en una línea JSON (`carpeta`, `cotizaciones`, `pdf`, `referencias`): es lo que leen `respaldo-diario.sh`, `actualizar.sh` y el despliegue. Los respaldos son confidenciales: incluyen las sesiones vigentes y la clave de IA cifrada.

Para el respaldo diario en el servidor, programa en el cron del host `scripts/respaldo-diario.sh <carpeta-en-otro-disco>`: respalda dentro del contenedor, ejecuta `npm run limpiar-borradores -- --confirmar` y copia el respaldo recién hecho a esa carpeta, donde conserva los 30 más recientes. La carpeta debe quedar fuera de la instalación. El cron de ejemplo y la preparación de la carpeta están en [docker/LEEME.md → Respaldo diario y limpieza](docker/LEEME.md#respaldo-diario-y-limpieza). `/api/salud` avisa si el último respaldo tiene más de dos días.

Para restaurar, con el servidor detenido: `npm run restaurar -- respaldos/cotizador-<fecha>` (`scripts/restaurar.ts`, `scripts/lib/restauracion.ts`). El comando verifica la copia con `integrity_check` (y que su esquema no sea más nuevo que esta versión) antes de tocar nada; se niega a seguir si el cotizador está en marcha (base en uso o un guardado en curso); aparta la base actual con sus `-wal`/`-shm`, `data/pdf/` y `data/referencias/` en `data/antes-de-restaurar-<fecha>/`, y restaura base, PDF, referencias y configuración del catálogo **del mismo respaldo**. Si algo falla a mitad de camino, devuelve los datos a como estaban. Borra la carpeta apartada cuando compruebes que todo está bien; para deshacer, restaura esa carpeta del mismo modo. Restaurar todo junto importa: si la carpeta `pdf` tuviera documentos más nuevos que la base, emitir fallaría al intentar reutilizar un número ya impreso (el cotizador nunca sobrescribe un PDF). En Docker, ver [docker/LEEME.md → Restaurar](docker/LEEME.md#restaurar).

### Limpieza de borradores

Los borradores que se eliminan desde la aplicación no se borran: van a una papelera, donde se ven y se restauran en **Historial → Papelera** (`restaurar_borrador`), hasta que `npm run limpiar-borradores -- --confirmar` los vacía tras el plazo de `--dias`.

`npm run limpiar-borradores` lista los borradores vacíos (sin ítems ni cliente) sin actividad en 30 días; `--dias N` cambia el plazo, `--con-items` incluye borradores con ítems y `--confirmar` los mueve a la papelera. En la misma pasada vacía de la papelera (borradores y productos eliminados del catálogo) lo que lleva ahí más de `--dias` días, y borra las referencias del cliente de `data/referencias/` que ningún ítem usa (las de un borrador que sigue en la papelera cuentan como usadas), si llevan más de 24 horas sin uso: así no se borra un archivo recién subido que todavía se está adjuntando. Sin `--confirmar` solo lista. Nunca toca cotizaciones con número. `scripts/respaldo-diario.sh` lo ejecuta cada día con `--confirmar`.

### Estado del sistema

`GET /api/salud` es el chequeo de salud del contenedor (healthcheck de `compose.yaml`). Sin sesión responde solo `{"ok": true}` con 200 o `{"ok": false}` con 503: la base abre con el esquema esperado, la configuración de inicio de sesión es válida, quedan más de 256 MB libres en el disco de datos y Chromium **arranca y abre una página** (plazo de 8 s; un arranque correcto se recuerda 10 minutos y una falla, 1 minuto, para no lanzar el navegador en cada healthcheck). Con sesión de administradora agrega el detalle de cada comprobación: versión del esquema, espacio libre, Chromium (ruta y cuándo se comprobó), clave de IA (configurada y legible; no llama a la IA, así que no confirma que sea válida ni que tenga saldo), Starken (si hay credenciales completas y ciudad de origen; no llama a Starken), última sincronización de feriados y fecha del último respaldo (aviso si tiene más de dos días). Nunca muestra secretos (`src/app/api/salud/route.ts`, `comprobaciones.ts`).

### Paridad con la planilla Excel

Requieren macOS con Microsoft Excel: rellenan la hoja `Cotización` de una copia de la planilla con lo que escribiría un vendedor, la recalculan con Excel y comparan. Los resultados quedan en `data/test-paridad-excel/` (fuera de Git).

- `npm run paridad:excel -- [--semilla N] [--limite N]` cotiza todos los productos de la planilla con el cálculo de la aplicación (`resolverItem` + `cotizar`), con cantidades, márgenes, flete y formatos de medida aleatorios, en cotizaciones de 1 a 24 líneas. No usa IA.
- `npm run paridad:excel-ia -- [--casos 150] [--semilla N] [--modelo id] [--anclaje corregir|avisar] [--solo-mensajes]` es de punta a punta: genera pedidos en lenguaje natural, los pasa por el mismo `Servicio` que la aplicación (IA de CommandCode, catálogo de la base y reglas de Ajustes, en una base temporal) y compara la cotización resultante con Excel usando en la columna % el margen de categoría. También cuenta los avisos: falsas alarmas en conversaciones correctas y graves avisadas o silenciosas. Llama al proveedor de IA.

### Precisión de la IA

`npm run evaluar:ia` corre los casos de `evals/cotizacion.json` contra el modelo configurado en Ajustes, con el mismo servicio que la aplicación y en bases temporales, y muestra la precisión por campo y las diferencias de cada caso. `--modelos a,b` compara modelos, `--anclaje corregir,avisar` compara los modos del anclaje, `--caso id` corre uno y `--min 0.95` sale con error bajo ese umbral. Informa llamadas, tokens, costo y latencia, y los avisos: falsas alarmas en corridas perfectas, errores avisados y errores silenciosos. Llama al proveedor real, así que tiene un costo pequeño por ejecución. Cada caso es una conversación (uno o más mensajes) y el pedido que debería quedar, incluido el precio neto escrito (`precioUnitario`) si lo hay; sin él, la IA no debe registrar ninguno. Lo mismo con el flete (`esperado.flete`, valor neto unitario y cantidad): sin él, un flete registrado es un error. Conviene sumar los pedidos reales que salgan mal. La IA no responde siempre igual: `--repeticiones N` corre cada caso N veces y lo cuenta como perfecto solo si las N corridas lo son, y `--min-perfectos 0.95` sale con error si menos del 95 % de los casos es perfecto. `--max-silenciosos N` sale con error si más de N errores de lectura llegaron sin aviso, y `--max-falsas 0.05`, si más del 5 % de las corridas perfectas avisó algo. Cada modelo (y modo de anclaje) deja su informe en `data/test-evaluar-ia/<fecha>-<modelo>.json` y `.md` (`--salida` cambia la carpeta): el resumen, los avisos por categoría (los de precio y flete tienen la suya) y las diferencias de cada caso, para compararlo con otra corrida sin volver a pagarla. Un caso puede exigir avisos y pendientes además del pedido. `npm run evaluar:regresion` es lo mismo con `--min 0.95 --min-perfectos 0.95 --max-silenciosos 0 --max-falsas 0.05 --repeticiones 3`, y `npm run deploy` lo corre antes de subir; con `--sin-ia`, el deploy lo omite y lo advierte en pantalla.

Antes de cambiar el prompt (`src/asistente/llm.ts`), el anclaje (`src/asistente/anclaje.ts`, `cobertura.ts`, `respuesta-directa.ts`) o el modelo:

1. `npm run test:unit`, `npm run typecheck` y `npm run lint`.
2. `npm run evaluar:regresion` con el modelo configurado.
3. `npm run paridad:excel-ia -- --casos 60 --semilla 2 --paralelo 1` y comparar con la corrida anterior (reporta aciertos, errores graves, latencia, tokens y costo). Con `--modelo id` se prueba otro modelo, con `--ids 3,7` se repiten conversaciones puntuales y con `--escenario marco,mixto` solo ciertos tipos de pedido; `--solo-excel` prepara antes el cálculo de Excel para correr varios modelos en paralelo.
4. Probar modelos de pago más caros solo con aprobación: cada corrida de 60 conversaciones cuesta entre US$ 0,02 (Qwen 3.7 Flash) y US$ 0,45 (modelos de gama alta).
5. Sumar a `evals/cotizacion.json` cada pedido real que salga mal.

`npm test` ejecuta toda la suite Vitest y después Playwright, sin filtros. La integración **falla** con un mensaje explícito si no está la planilla real; no se omite ni se sustituye por un catálogo inventado.

Incluye los ocho oráculos de precios (neto $4.523.269, IVA $859.421, total $5.382.690), conteos, 29 correcciones, campos permitidos, errores de plantilla, normalización, huecos de ancho, tolerancia de altos, cantidades, redondeo, ajustes, preguntas, contexto sin precios, respuesta inválida, correlativos concurrentes, reinicio, fallos de PDF, inmutabilidad y bloqueo de aprobación.

## Límites y diferencias documentadas

- Se usó un lector selectivo de XML en lugar de `exceljs` para mantener la restricción de no leer las columnas H–N. Las tablas auxiliares sí se obtienen del archivo.
- Se bloquea la emisión con ítems incompletos para impedir una cotización parcial accidental. Editar una emitida abre una nueva revisión como borrador.
- La paridad se valida contra los ocho oráculos sobre la planilla real y, en macOS con Excel, con `npm run paridad:excel` y `npm run paridad:excel-ia` (ver «Paridad con la planilla Excel»).
- La meta de respuesta en menos de cinco segundos depende de la disponibilidad de CommandCode y del modelo. El E2E prueba un adaptador fijo; no acredita latencia del proveedor. Un vencimiento del plazo devuelve HTTP 504 (`ia_timeout`) y conserva el borrador. Los errores de acceso, configuración, límite y disponibilidad se muestran con mensajes específicos sin revelar la respuesta cruda ni las credenciales.
- No incluye Puertas Flores SPA, muebles, registro público, recuperación de contraseñas por correo ni envíos a clientes. Quedaron fuera del alcance de octubre de 2026 las devoluciones de pagos (anular un pago es todo o nada), las copias de respaldo y alertas fuera del servidor (el respaldo diario copia a otro disco del mismo servidor; `/api/salud` no avisa por correo ni mensajería), los favoritos o plantillas (solo «Duplicar»), la actualización masiva de precios (solo reimportar), la verificación en dos pasos y deshacer un turno completo del chat (Deshacer cubre los ítems). Las familias y las reglas de precios siguen limitadas a los valores documentados.

## Prueba remota con acceso restringido

Con Docker, `compose.yaml` incluye un servicio `tunel` opcional (un Cloudflare Tunnel propio de la cuenta del dominio) que se activa con `COMPOSE_PROFILES=tunel` y `CLOUDFLARE_TUNNEL_TOKEN` en el `.env` del servidor; en el panel de Cloudflare, el hostname apunta a `http://cotizador:3000` (ver [docker/LEEME.md → Túnel de Cloudflare propio](docker/LEEME.md#túnel-de-cloudflare-propio)). Sin Docker, sigue la [guía oficial de aplicaciones protegidas con Access](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/). Para una demostración remota, crea en Cloudflare Zero Trust una aplicación **Access** para el hostname, con una política Allow limitada a los correos autorizados. Después configura un Cloudflare Tunnel cuyo servicio sea `http://127.0.0.1:3000`, asociado a ese hostname; configura `NELTUME_HOSTS` con el hostname, `BETTER_AUTH_URL` con su origen `https://` y un `BETTER_AUTH_SECRET` propio. El túnel debe apuntar a la versión de producción (`npm run build && npm start`), nunca a `npm run dev`: el modo desarrollo confía en orígenes loopback adicionales, muestra errores detallados y no exige las validaciones de producción. La aplicación exige además una cuenta local. No uses un Quick Tunnel público ni expongas el puerto directamente.

Medidas de seguridad activas: todas las cuentas tienen rol `admin`; las rutas `/api/auth/admin/*` siguen respondiendo 404 y la creación se limita a la ruta propia de Ajustes; el inicio de sesión se limita a 5 intentos por IP cada 15 minutos (la IP sale solo de la cabecera de `NELTUME_IP_HEADER`, `cf-connecting-ip` por omisión; con `ninguna`, o si el proxy no la envía, todas comparten el mismo límite) y a 10 fallos por correo cada 15 minutos; en las escrituras, `Origin`, si viene, debe coincidir con el Host, y `Sec-Fetch-Site`, si viene, debe ser `same-origin` (`src/servidor/acceso.ts`); nadie puede desactivar su propia cuenta ni la última administradora activa; cambiar el correo o la contraseña de una cuenta desde Ajustes exige la contraseña propia (5 intentos fallidos cada 15 minutos); una cuenta desactivada responde al inicio de sesión igual que una contraseña incorrecta (401); los inicios de sesión correctos y fallidos quedan en el registro de cambios de Ajustes → Usuarios (correo, dispositivo e IP, nunca la contraseña), y en Ajustes → Mi cuenta cada persona ve sus sesiones abiertas y puede cerrar una o todas las demás (`/api/sesiones`); todas las respuestas incluyen `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: same-origin` y, en producción, HSTS. Los PDF se descargan por defecto; `?ver=1` los abre en el navegador. `/api/logo` exige sesión (la página de inicio de sesión usa el archivo estático `/logo-neltume.svg`); el SVG subido se valida con un parser que solo acepta elementos y atributos de dibujo (`src/servidor/svg-seguro.ts`) y se sirve con `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` y `nosniff`.

Subidas: la importación de Excel (`src/app/api/catalogo/importar/route.ts`, hasta 20 MB) y las referencias del cliente (`src/app/api/referencias/route.ts`, hasta 10 MB) exigen `Content-Length`: sin él responden 411, y si el tamaño declarado o el que llega supera el tope, 413, sin cargar más que eso en memoria. Al leer el `.xlsx`, lo descomprimido no puede pasar de 200 MB en total ni de 100 MB por parte (`LIMITES_DESCOMPRESION`, `src/catalogo/xlsx.ts`); un libro que se infla más se rechaza antes de descomprimir.
